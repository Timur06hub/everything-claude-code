# Замер производительности цепочки хуков ECC

Дата замера: 2026-10-30. Основа: `origin/main` на коммите `b38be6a7`, Node v22.22.0, 4 ядра, loadavg 0,4 → 1,0.
Код ECC и пользовательские настройки не менялись, хуки в `settings.json` не подключались.

## Итоги

1. Отключённый хук стоит 63–88 мс при 30 мс у голого Node (в 3,1–3,9 раза больше). Проверка «включён ли хук» выполняется после запуска обоих процессов Node, поэтому `ECC_DISABLED_HOOKS` почти ничего не экономит.
2. Больше всего времени занимает слой bootstrap: около 50–55 мс (второй процесс Node плюс загрузка модулей). Встроенный фрагмент `node -e`, который ищет корень плагина, стоит около 0–12 мс.
3. Работа самих хуков невелика, кроме `observe` и `Stop`: диспетчер `pre-bash` +11 мс, gateguard +19 мс, `PostToolUse`-диспетчер +38 мс, `Stop` +72 мс, `observe` +334 мс.
4. `observe` — главный выброс: около 434 мс и 36 дополнительных процессов (8 запусков `python3`) на каждый вызов любого инструмента. Хук асинхронный и вызов не блокирует, но грузит CPU.
5. Раньше расходились две оценки: около 100 мс на отключённый хук (подтвердилось, 93–118 мс) и 2 мс (замер в обход bootstrap, для реальной цепочки не годится).

## Какие цепочки существуют

| Тип | Цепочка | Node-процессов |
|---|---|---|
| A | `node -e` → `plugin-hook-bootstrap` → `run-with-flags` → хук | 2 (3, если хук не экспортирует `run()`) |
| B | `node -e` → `plugin-hook-bootstrap` → диспетчер `pre-bash` | 2 |
| C | `node -e` → `posttooluse-dispatcher.cli()` | 1 |
| D | `node -e` → `lifecycle-hook-bootstrap.cli()` → `run-with-flags` → хук (`Stop`) | 2–3 |

## Методика

- 30 измеряемых запусков и 3 прогревочных на каждый из 28 случаев, раунды чередуются со сдвигом начала.
- Запуск через `sh -c` с JSON на stdin, как это делает Claude Code. Изолированные `HOME`, `TMPDIR`, `CLAUDE_PROJECT_DIR`, в проекте пустой git-репозиторий. `CLAUDE_PLUGIN_ROOT` задан явно.
- Процессы считались по `execve` через `strace -f`, по 3 запуска на случай, отдельным проходом (на замер времени `strace` не влиял).
- Аудит безопасности: тот же `strace` по системным вызовам записи и `connect`.

## Что измерено, а что оценка

- Измерено напрямую: все времена, число процессов по `execve`, выходные коды, аудит записей и сети.
- Вычислено арифметически из измеренного: вклад слоёв, разницы «включён − отключён», кратность к голому Node, z-оценка (предполагает примерно нормальное распределение).
- Оценки, которых не измеряли: разбиение слоя bootstrap на «второй Node» и «загрузка модулей»; суммарная стоимость на один вызов инструмента (для `Bash` совпадает около 10 процессов Node, порядок величины около 1 с последовательно); выигрыш от рекомендаций; параллельность хуков в самом Claude Code.
- Не покрыто: путь запрета gateguard (измерен путь «разрешить»); медленный путь поиска корня плагина без `CLAUDE_PLUGIN_ROOT`; `governance-capture`, `session-start`, асинхронный `PostToolUse`-диспетчер; профиль `minimal`; сам Claude Code.

Полезная нагрузка безопасна: диспетчер `pre-bash` только анализирует команду `echo hello`, а не выполняет её. Хуки, ходящие в сеть (`mcp-health-check`), не запускались.

## Рекомендации

Это выводы из данных, а не правки. Оценки выигрыша приблизительные.

1. Принимать решение «включён ли хук» в первом процессе по переменным окружения, не запуская `run-with-flags`. Отключённый хук подешевел бы примерно с 95–118 мс до 45–70 мс.
2. Вызывать `run-with-flags` через `require` вместо `spawnSync`: слой bootstrap даёт 50–55 мс из около 100 мс цепочки.
3. Склеить `PreToolUse`-записи в один диспетчер на событие. У `PostToolUse` это уже сделано: один Node и 71 мс в отключённом состоянии против 93–118 мс у остальных.
4. Переписать горячий путь `observe` на один процесс Node или прореживать запись: около 434 мс и 36 процессов на вызов.
5. Измерить дальше то, что перечислено в «Не покрыто».
